大模型选型指南：一个具身智能学习者的思考

入坑具身智能一段时间了，最近在学 Agentic 工具链的过程中顺带梳理了一下主流模型。从一个学习者的视角，聊聊我对”具身智能研究用什么模型”这个问题的理解和思考。

一、我为什么会关注模型选型

最开始接触大模型的时候，我的用法很简单：打开一个对话框，把问题丢进去，等答案。

现在开始学习具身智能，慢慢发现事情没那么简单。具身智能这个方向，技术栈又深又杂：ROS2、仿真器（MuJoCo / Isaac Lab）、机器人 URDF 建模、强化学习、模仿学习、Sim2Real……随便一个环节都可能要跟代码、论文、配置文件打交道。这时候，用什么模型、怎么用，就从一个无关紧要的问题变成了直接影响效率的事情。

我最近花了一些时间了解市面上的主流模型，结合我对具身智能研究流程的理解，整理了这份选型思考。

声明：我还在学习阶段，很多具身智能的具体工作（比如完整的论文复现、真机部署）我还没有亲手做过。下面更多是基于”我了解到具身智能研究会涉及这些环节”的推演和分析，而非实战经验总结。

二、具身智能研究到底需要大模型做什么

在聊具体模型之前，先梳理一下：具身智能研究者日常可能会遇到哪些需要大模型帮忙的事情？

我目前的理解是，大概有这几类：

第一类：啃论文、理解架构

具身智能领域的论文通常信息密度很高——系统架构图、数学公式、代码片段、实验配置表全挤在一起。一篇 manipulation 方向的论文可能有十几页，读完还要能把它的思路映射到代码上。这个过程的痛点不是”看不懂某句话”，而是信息太多、跨度太大，靠自己梳理很慢。

第二类：写代码、调 Bug

具体到代码层面，涉及的东西也很多样：ROS2 节点通信、仿真场景搭建（URDF/SDF 模型文件、YAML 配置）、训练脚本（PyTorch + RL 算法）、推理部署（ONNX 导出、TensorRT 量化）。这些东西分布在不同的文件和目录里，牵一发动全身。

第三类：推公式、理解算法

运动学/动力学的数学推导、强化学习里的策略梯度、扩散模型的原理……具身智能的算法门槛不低。有时候一个公式卡半天，需要一个能耐心做链式推理的帮手。

第四类：写文档、做记录

实验记录、周报、技术博客。这类事情对智力的要求不高，但对效率的要求高——最好又快又省。

每类任务的形态差异很大，所以不太可能一个模型包打天下。

四、按场景推演：具身智能各环节适合什么模型

这部分是我的推演和分析，基于我对具身智能研究流程的理解，以及我实际用过一些模型后的感受。

场景 1：论文阅读理解

典型需求：把一篇 10-20 页的论文（含架构图、公式、实验结果表）快速吃透，理清核心思路和工程实现要点。

关键能力：超长上下文 + 多模态（读图）+ 结构化总结

我的分析：这是 Gemini 2.5 Pro 最舒服的场景。1M 上下文意味着可以把整篇 PDF 直接扔进去，不用分段。而且 Gemini 的多模态能力能直接理解论文里的系统架构图和网络结构图，不用你自己先把图画一遍。相比之下，纯文本模型读不了图里的信息，得靠自己补。

如果是看中文论文或者中文技术博客，DeepSeek V4 也完全够用，1M 上下文，中文理解好，还便宜得多。

预算友好方案：DeepSeek V4（论文阅读够用，不用花 Gemini 的钱）

场景 2：代码开发与调试

典型需求：写 ROS2 节点、搭建仿真场景、调训练脚本、修 Bug。

关键能力：代码生成质量 + 跨文件理解 + 错误诊断

我的分析：这部分Claude Sonnet 4.6 是目前公认最强的性价比之选。我自己在对比实验中也有体会——同样是在嵌入式项目中新增一个模块，Claude（通过 Cursor）一次跑通，而千问反复报错修不好。

这里还有一个值得注意的工具选择问题：Agent 架构 vs IDE 补全。Claude Code 采用的是独立 Agent 模式——你把任务交给它，它自己规划、执行、验证，像一个独立开发者。Cursor 是 IDE 协作模式——侧重人机实时交互。实测数据上，Claude Code 在复杂多文件任务上的成功率约 72%，传统 IDE Agent 约 55%–62%。

对于具身智能开发中的跨文件问题（比如改一个 ROS 话题名，要同步改 publisher、subscriber、launch 文件、config），Agent 架构的全局视角优势很明显。

预算友好方案：DeepSeek V4（通过 cc-switch 接入 Claude Code，每月几乎不花钱）

场景 3：数学推导与算法理解

典型需求：理解论文里的数学推导，分析 RL 算法的收敛性，搞清楚某个动力学公式怎么来的。

关键能力：长链推理 + 数学严谨性

我的分析：这类场景适合OpenAI o 系列。o4-mini 的推理能力就很不错了，价格只要 o3 的十分之一。日常推导用 o4-mini 完全够，不用杀鸡用牛刀。

不过说实话，对大多数学习者来说，这个场景可能不会特别高频——更多是用在啃理论性强的论文或者准备组会分享的时候。

预算友好方案：o4-mini（推理够用，价格友好）

场景 4：日常写作与文档

典型需求：写实验记录、周报、技术博客、整理学习笔记。

关键能力：表达清晰 + 速度快 + 便宜

我的分析：Gemini 2.5 Flash 是这个场景的答案。它推理深度肯定不如 Opus 或 o3，但写文档不需要那么深的推理。Flash 快、便宜（输入 $0.30/MTok），能处理长上下文（比如你要总结一周的实验日志）。DeepSeek V4 也是好选择，中文表达甚至更自然。

预算友好方案：DeepSeek V4（中文写作体验好，极低成本）

场景 5：批量处理

典型需求：标注实验数据、清理日志、批量提取结构化信息。

关键能力：速度 + 成本 + 大吞吐量

我的分析：Gemini 2.5 Flash 就是为这个设计的。便宜到几乎可以忽略成本，快到几乎没有等待感。1M 上下文也足够处理长序列的传感器数据日志。

六、一个学生的省钱组合

具身智能方向的学生，个人在模型上的预算不多。我给自己的规划是这样的：

如果预算更紧张，那就 DeepSeek V4 一把梭。它编程能力不如 Claude原模型，推理不如 o 系列，但除了无多模态外每个方面都不差，1M 上下文、中文友好、价格极低。对于学习阶段的大部分需求完全够用。

七、几点不成熟的感想

在梳理模型选型的过程中，我有几个比较深的感受：

1. 上下文窗口是硬门槛

具身智能和纯软件工程不一样。纯软件工程你面对的是代码，几十万 token 的上下文通常够了。但具身智能你要同时面对论文 PDF、代码仓库、仿真配置，这些东西加在一起可能几十万甚至上百万 token。1M 上下文不是奢侈品，是刚需。

2. 不同模型有各自的”甜点区”

以前我以为”用最好的模型就行了”。后来才意识到，不同模型在不同任务上的差距是真实存在的，而且是互补的：

  • Gemini 强在多模态 + 大上下文，适合”理解”类任务
  • Claude 强在编程和 Agent，适合”执行”类任务
  • o 系列强在推理，适合”思考”类任务

组合使用不是折腾，是真的能提效。

3. Agent 工具的选择可能比模型本身还重要

同样的模型（比如 Claude Sonnet），通过 Cursor 用和通过 Claude Code 用，体验完全不同。具身智能开发中的很多问题需要跨文件理解和多步骤修改，这种场景下 CLI Agent 的架构优势比单纯的模型能力差异更明显。

4. 对学习者来说，够用就好

我的很多分析是基于”具身智能研究者日常会做什么”的推演，但实际上作为学习者，很多高阶场景（比如完整的论文复现、真机部署调试）我暂时还不会高频碰到。所以现阶段选模型不需要追求”最强”，性价比高、覆盖面广更重要。DeepSeek V4 + 偶尔按需调用 Claude/Gemini，对学习阶段来说是一个很舒服的配置。

本文是我在学习 Agentic 工具链和具身智能过程中的阶段性思考。模型数据和价格参考 2025 年中，实际情况会持续变化。如果你也在学习这个方向，欢迎交流。
